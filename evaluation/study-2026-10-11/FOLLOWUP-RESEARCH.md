# Retrieval that moves work into the index

**Primary-source access: 2026-10-12 UTC; local study date: October 11. Research proposals only.** The expanded experiment was unfinished when this note was prepared. Its [prospective plan](PLAN.md), [execution amendment](EXECUTION-AMENDMENT.md) and [report draft](REPORT.md) govern the running comparison. This followup changes none of its frozen inputs or schedules. No models, dependencies or indexing implementations were added for this review. It complements [MODEL-RESEARCH.md](MODEL-RESEARCH.md).

The useful alternative to repeatedly scoring query–document pairs is to represent documents once, then search those representations. That moves work and storage into indexing; it does not eliminate query computation or guarantee governing evidence. Accuracy and complete context remain the objective. A local score or classifier can be an optional component, with deterministic evidence expansion and source-version checks evaluated separately.

| Method | Index and update work | CPU query work | Boundary and exact license |
|---|---|---|---|
| BM25 plus explicit rules | Token postings, aliases and validated fields | Lexical ranking, exact-ID lookup, field checks | Metadata correctness is an input; no learned weights |
| Dense bi-encoder | Store document/chunk vectors; recompute changed inputs | Encode query once, then vector similarity | Sentence Transformers code and inspected all-MiniLM-L6-v2 card: Apache-2.0 |
| NAVER SPLADE family | Learned term weights/expansion; sparse postings | Learned query representation, then sparse matching | Inspected code and two named checkpoints: CC BY-NC-SA 4.0 |
| OpenSearch document-only sparse | Learned document vectors; tokenizer/weight assets | Tokenization, fixed weight lookup, sparse matching | Inspected neural-search code and doc-v2-distill card: Apache-2.0 |
| ColBERTv2/PLAID | Compressed token vectors and search structures; official workflow requires GPU indexing | Query token encoding, candidate search, token interaction; CPU search supported | Official code and colbertv2.0 card: MIT |
| Supervised shallow tree | Labeled examples, features, fitting and validation | Feature calculation and tree traversal | scikit-learn code: BSD-3-Clause; no pretrained branch knowledge |

These are architectural work allocations, not measured latency rankings. Index construction, refresh cost, storage, warm query latency and returned context must be reported separately.

## Dense and sparse candidate generation

A bi-encoder stores corpus embeddings and embeds a new query once. For this study's small collections, exact vector similarity is a useful initial baseline before approximate nearest-neighbor indexing adds another recall tradeoff. The official documentation explicitly warns that approximate search can miss high-similarity vectors. The inspected `sentence-transformers/all-MiniLM-L6-v2` checkpoint supplies a 384-dimensional representation but truncates beyond 256 word pieces by default. It is a concrete general embedding baseline, distinct from the cross-encoder already running; its short-paragraph training does not establish best performance for asymmetric memory queries. Freeze chunking and test corrections beyond the first window. [FR03: semantic-search documentation](https://www.sbert.net/examples/sentence_transformer/applications/semantic-search/README.html), [exact checkpoint card](https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2)

SPLADE learns sparse vocabulary weights and expansion using a masked-language-model head, allowing an inverted index to support learned retrieval. Sparsity is a model/training choice with effectiveness tradeoffs, rather than an assurance of BM25-like local speed. The inspected NAVER repository and `naver/splade-cocondenser-ensembledistil` and `naver/splade-v3` cards all specify CC BY-NC-SA 4.0. Describe those exact releases as noncommercial code/weights, not unrestricted open-source candidates. The v3 card also displays a contact-sharing access gate; no access was requested. [FR01: official code and license](https://github.com/naver/splade), [SPLADE++ paper, method and evaluation](https://arxiv.org/html/2205.04733v2), [cocondenser card](https://huggingface.co/naver/splade-cocondenser-ensembledistil), [v3 card](https://huggingface.co/naver/splade-v3)

An Apache-2.0 alternative is `opensearch-project/opensearch-neural-sparse-encoding-doc-v2-distill`. Its exact example runs the model on documents, while a query becomes token presence multiplied by the supplied `idf.json` lookup. The similarly named checkpoint without `doc` runs learned encoding on both sides. “Inference-free” therefore refers to neural query inference, not indexing, tokenization or retrieval. The associated paper examines document-only sparse retrieval, but its reported BERT-base experiment must not be treated as a benchmark of this exact DistilBERT release or this machine. [FR02: document-only checkpoint](https://huggingface.co/opensearch-project/opensearch-neural-sparse-encoding-doc-v2-distill), [query-and-document checkpoint](https://huggingface.co/opensearch-project/opensearch-neural-sparse-encoding-v2-distill), [paper v2](https://arxiv.org/html/2411.04403v2), [official code license](https://github.com/opensearch-project/neural-search/blob/main/LICENSE)

## Late interaction and hybrid search

ColBERT stores token-level document vectors and encodes query tokens at search time. MaxSim aggregates each query token's best document-token match; it retains finer interactions than a single document vector without a fresh joint transformer pass for each pair. PLAID adds centroid-based candidate filtering and optimized interaction/decompression. Its CPU experiments use a specified server configuration and thread limits; they cannot predict this desktop's performance. The official README supports CPU execution but states that training and indexing require a GPU. Its updater exposes add/remove/persist operations, not automatic discovery of filesystem corrections. A future adapter must maintain passage-ID-to-source-version mappings and verify refresh after restart. [FR04: official repository](https://github.com/stanford-futuredata/ColBERT), [PLAID methods and setup](https://arxiv.org/html/2205.09707v1), [updater source](https://github.com/stanford-futuredata/ColBERT/blob/main/colbert/index_updater.py), [MIT checkpoint card](https://huggingface.co/colbert-ir/colbertv2.0)

A prospective hybrid arm can union lexical, semantic and explicit-ID candidates under fixed per-channel limits, then compare rank fusion with the same final context allowance. OpenSearch documents reciprocal rank fusion and distinguishes pre-filtering from post-filtering. Its exact-term guidance warns against using analyzed text fields for literal identity. These support the mechanism, not deploying an OpenSearch cluster here or assuming fusion improves completeness. [FR05: hybrid search](https://docs.opensearch.org/latest/vector-search/ai-search/hybrid-search/index/), [exact-term matching](https://docs.opensearch.org/latest/query-dsl/term/term/)

## Metadata boundaries and future tests

The following are proposed policies, not source-proven capabilities. Store explicit entity IDs, namespaces, aliases, scope, effective intervals, supersession/dependency links and provenance as retrieval features. Use hard scope filters only for explicit task constraints and validated fields. Missing, ambiguous or inferred scope should remain eligible for global retrieval; folder membership cannot establish applicability. An exact identifier should retrieve its record and related correction/dependency chain, rather than suppress all differently named governing evidence. File modification time is not decision-effective time. Unresolved authority stays inspectable.

Every stored representation needs a source ID/version, content digest, chunk boundaries and transform/model/tokenizer revision. Include metadata changes in invalidation. Editing a source rebuilds affected representations; adding a correction updates reverse links and invalidates dependent derived views and cached packets. Retain originals, including historical versions. At retrieval, resolve pointers against the current index snapshot and original text. A valid ledger does not certify the derived prose.

A shallow supervised classifier could consume lexical scores, entity matches, scope agreement and version features. scikit-learn's tree documentation requires training samples and class labels and describes overfitting and instability. Labels, held-out workstreams, an unknown-class policy and calibrated routing thresholds would be new experimental work. This is not free zero-shot branch discovery; feature extraction cost belongs in query timing. [FR06: tree documentation](https://scikit-learn.org/stable/modules/tree.html), [code license](https://github.com/scikit-learn/scikit-learn/blob/main/COPYING)

After the frozen experiment completes, predeclare independent comparisons: cached dense retrieval; lexical/semantic union; document-only sparse retrieval; explicit-ID candidate addition; source/metadata invalidation; and optional branch classification. Compare each with its own baseline before combinations. Branch-pruning arms need an always-executed, fixed-budget global fallback that searches the full eligible collection. Report evidence excluded by routing, rescued corrections, sufficient-original bundle recovery and downstream source use. Add restart/update, wrong-scope, missing-metadata and late-correction cases. Accept fewer tokens or lower latency only when governing evidence remains complete.
