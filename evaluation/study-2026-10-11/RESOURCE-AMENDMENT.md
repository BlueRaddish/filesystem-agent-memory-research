# Resource cap for recovered collection

The original [freeze.json](freeze.json), [execution-freeze.json](execution-freeze.json), [execution amendment](EXECUTION-AMENDMENT.md) and resumable runner remain unchanged. This additional operational amendment caps actual factorial concurrency at two workers. The frozen runner still receives its required `workers=4` argument; [run_resource_safe.py](run_resource_safe.py) substitutes a `ThreadPoolExecutor` subclass that rejects every requested count except four and constructs a pool with an actual maximum of two. No ranking, eligibility, packing, model, tokenizer, batch, prompt, byte budget, family split, reader schedule or outcome rule changes.

The preceding four-worker recovery was stopped after an observed PowerShell CLR initialization failure and host memory-pressure observations. At the recorded observation, available physical memory was approximately 795 MB of 16.91 GB, and available commit was approximately 1.14 GB of 32.64 GB. Those observations motivate a resource cap; they do not prove a specific cause of model slowness or the CLR failure. Only the identified coordinator and its owned child were stopped, using process identity checks. Sixteen complete task checkpoints, representing 3,072 retrieval packet rows, were preserved. Their settled byte hashes are pinned by the root-created `resource-freeze.json` before restart. No other host processes were modified.

The wrapper first uses the original `verify_execution` checks for corpus, original freeze, recovery amendment, model files and runner identity. It then verifies its own code/amendment hashes, base identities, requested/actual worker pins and every previously accepted task-checkpoint hash against `resource-freeze.json`. It writes a private `resource-started.json` history in the existing external work directory before the long run. That history records the resource-freeze hash, requested four/actual two worker configuration, attempt ID and current checkpoint hashes. Extra completed task checkpoints on a later resume require a matching nonempty resource-start history. The frozen runner's existing input-pin, envelope-digest and reconstructed-packet validation still checks every chunk before reuse. A history entry alone does not validate a chunk.

After successful original execution, all checkpoint bytes present at wrapper start must retain identical hashes. The original runner continues to require exact agreement with all 576 preserved interrupted outcome rows before publishing its full result. A public `resource-receipt.json` records the actual cap, checkpoint reuse count and hashes, public worker run IDs and model-manifest hashes, separating reused workers from fresh run IDs. It contains no private filesystem paths, process IDs or account information. The receipt overrides the historical four-worker wording retained in the unchanged `model-execution.json` timing-limit field: reused chunks precede this cap; fresh collection uses at most two workers. Factorial receipts include cache reuse and concurrent contention, and do not estimate isolated engine latency.

The separately planned 144 uncached warm timing observations remain serial with two intra-op threads per model, unchanged batch size and pinned weights/tokenizers. Unknown retrieval work from an incomplete task may be recomputed from its task boundary. A scored reader completion is never retried or replaced. This is an operational scheduling response to observed resource pressure, not tuning based on held-out outcomes. The cap bounds this pool's concurrency; it does not certify resource availability elsewhere on the host.

The runnable `--selfcheck` uses fake tasks and temporary fixtures only. It verifies a peak of two concurrent fake tasks, rejects a different requested worker count, rejects changed base/amendment pins, and requires matching resource-start provenance for extra resumed checkpoints. It performs zero model calls. Complete output equivalence and the 576-row overlap remain execution gates, not results claimed by that selfcheck.
